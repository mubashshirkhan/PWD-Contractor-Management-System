# MahaTenders SQLite to Neon PostgreSQL Migration Plan

## Status and scope

This is a design-only migration plan. It has not connected to Neon, executed
SQL, modified SQLite, run migrations, or changed backend behavior.

The target is one PostgreSQL database with two independent schemas:

- `main`: the existing `mahatenders.sqlite3` dataset.
- `location_ui`: the existing `location_ui_test.sqlite3` dataset.

Tender records must not be merged across schemas. The 13 tender IDs shared by
the SQLite databases remain separate records because each schema has its own
tables and identity sequences.

The PostgreSQL DDL is in
[`postgres_schema.sql`](./postgres_schema.sql).

## Existing audit facts

The latest read-only audit found:

- Main `tenders`: 85 rows.
- Location `tenders`: 63 rows.
- Main `source_evidence`: 267 rows.
- Location `source_evidence`: 402 rows.
- Main coverage tables exist but contain zero rows.
- Location coverage tables do not exist.
- No duplicate primary keys.
- No duplicate values under declared unique constraints.
- No invalid JSON values were found in checked JSON fields.
- Seven main `tender_occurrences` reference missing tender IDs.
- Thirteen tender IDs occur in both SQLite databases.
- Portal date values are stored as strings such as `09-Nov-2026 03:00 PM`.

## Schema design

### `main`

The main schema contains:

- `organisations`
- `tenders`
- `source_evidence`
- `extraction_runs`
- `run_organisations`
- `listing_pages`
- `extraction_errors`
- `tender_occurrences`
- `coverage_runs`
- `coverage_partitions`
- `coverage_pages`
- `coverage_tender_work`
- `tender_observations`
- `schema_migrations`

Coverage tables are included because they are part of the main database
migrations, even though they are currently empty.

### `location_ui`

The location schema contains the base tables:

- `organisations`
- `tenders`
- `source_evidence`
- `extraction_runs`
- `run_organisations`
- `listing_pages`
- `extraction_errors`
- `tender_occurrences`

The location database does not receive coverage tables because the audit found
none there and the existing location workflow does not use them.

## Type and preservation decisions

### Integer IDs

SQLite integer primary keys become:

```sql
BIGINT GENERATED BY DEFAULT AS IDENTITY
```

`BY DEFAULT` is intentional: migration imports can insert the original SQLite
IDs explicitly. PostgreSQL sequences must be advanced after import.

### Portal dates

Existing date-bearing columns remain `TEXT` in the first migration. This
preserves the original portal strings exactly and avoids changing API behavior.

After migration, optional typed date columns may be introduced separately, but
they must be derived values and must never replace the original text.

### JSON

Existing JSON strings remain `TEXT`:

- `summary_json`
- `parsed_fields_json`
- `source_evidence.raw_value` values containing detail JSON

The original text must be imported byte-for-byte. Optional `jsonb` shadow
columns may be added later only for records that parse successfully. They must
not replace or normalize the original values.

### Foreign keys

Declared SQLite relationships are retained:

- Run tables reference extraction runs.
- Listing pages and errors reference extraction runs.
- Main `source_evidence` references main tenders.
- Coverage children reference coverage partitions.
- Observations reference tenders and coverage partitions.
- Location `tender_occurrences` reference location tenders.

The location `source_evidence.tender_id` remains a logical association because
that SQLite schema does not declare a foreign key for it. The audit found no
orphan evidence rows.

The main `tender_occurrences` foreign key is not part of the initial schema
creation. It is added only after all main rows, including the seven orphans,
have been imported:

```sql
ALTER TABLE main.tender_occurrences
    ADD CONSTRAINT tender_occurrences_tender_fk
    FOREIGN KEY (tender_id) REFERENCES main.tenders(tender_id)
    NOT VALID;
```

This preserves every historical row while rejecting new invalid references.
The constraint must not be validated until an explicit orphan-resolution
decision is approved. No missing tender records will be invented.

## Migration procedure

### 1. Freeze and verify source files

Before import:

1. Stop extraction and cleanup writers.
2. Keep the original SQLite files unchanged.
3. Create separately stored backups.
4. Record SHA-256 hashes and file sizes.
5. Open backups read-only.
6. Record table names, schemas, row counts, primary keys, unique indexes,
   foreign-key checks, and tender-ID sets.

### 2. Create the target database and tables

1. Create one Neon PostgreSQL database.
2. Apply the table/index portion of `postgres_schema.sql` in a controlled
   migration transaction. Do not execute the commented main orphan-constraint
   statement yet.
3. Confirm both schemas exist.
4. Confirm no target table contains data before import.
5. Restrict application roles so API reads and extraction writes have only the
   required permissions.

The DDL must be reviewed before execution. This plan does not execute it.

### 3. Import main parent and dependent data

Import in dependency order:

1. `main.organisations`
2. `main.extraction_runs`
3. `main.tenders`
4. `main.run_organisations`
5. `main.listing_pages`
6. `main.source_evidence`
7. `main.tender_occurrences`, including all seven orphan rows
8. `main.extraction_errors`
9. `main.coverage_runs`
10. `main.coverage_partitions`
11. `main.coverage_pages`
12. `main.coverage_tender_work`
13. `main.tender_observations`
Migration history is not imported from either SQLite source. PostgreSQL
`main.schema_migrations` is managed independently by
`postgres_migrations.py`.

Use explicit column lists. Never use `SELECT *` for migration transforms.

### 4. Add the main occurrence constraint after import

Only after step 3 completes:

1. Add `main.tender_occurrences_tender_fk` using `NOT VALID`.
2. Run a read-only violation report.
3. Confirm the result contains the original seven orphan rows and no newly
   introduced violations.
4. Do not run `VALIDATE CONSTRAINT` yet.

The constraint is therefore absent while orphan rows are loaded, but it
rejects new invalid references once installed.

### 5. Import location data

Import in dependency order:

1. `location_ui.organisations`
2. `location_ui.extraction_runs`
3. `location_ui.tenders`
4. `location_ui.run_organisations`
5. `location_ui.listing_pages`
6. `location_ui.source_evidence`
7. `location_ui.tender_occurrences`
8. `location_ui.extraction_errors`

The location occurrence foreign key is created by the schema and is satisfied
by importing `location_ui.tenders` before `location_ui.tender_occurrences`.
The location schema has separate identity sequences and separate unique
constraints. A tender ID that also exists in `main.tenders` must not conflict.

### 6. Preserve and verify the seven orphan occurrences

The seven audited main occurrences must be imported exactly as recorded,
including:

- Original integer `id`
- Original `tender_id`
- Search taluka
- Listing URL
- Page number
- Observation timestamp

They must not be deleted, renamed, or assigned fabricated tender rows.

After the rows are imported and the post-import constraint is added:

1. Query and document the seven violations.
2. Confirm no additional violations were introduced.
3. Confirm the `NOT VALID` constraint rejects new invalid references.
4. Decide separately whether the portal records can later be re-associated.
5. Only validate the constraint after all historical orphans are resolved.

### 7. Adjust identity sequences

For every identity-backed table in both schemas, including
`organisations`, `tenders`, `source_evidence`, `extraction_runs`,
`listing_pages`, `extraction_errors`, `tender_occurrences`, and all main
coverage tables:

1. Read the maximum imported `id`.
2. Set the PostgreSQL identity sequence to at least that value.
3. Verify that the next generated insert does not collide.

This must be done independently in `main` and `location_ui`.

The implementation should use the identity sequence associated with the
qualified table, not a shared global sequence. Conceptually, each sequence
must be advanced to `MAX(id)` (or its documented empty-table baseline) before
any new application write is enabled. Existing IDs are imported explicitly;
future IDs are generated only after this adjustment.

### 8. Validate imported data

Compare source and target:

- Row counts for every table.
- Primary-key sets.
- Unique-key sets.
- Tender-ID sets per schema.
- The 13 cross-schema overlap IDs.
- Source-evidence counts and content hashes.
- JSON text hashes.
- Raw date-string hashes.
- Scope-status distributions.
- Foreign-key violations.
- Coverage table counts.
- Representative complete tender records.

Expected tender counts:

```text
main.tenders       = 85
location_ui.tenders = 63
```

Expected overlap is 13 IDs across schemas, not duplicate rows within one
schema.

### 9. API compatibility validation

Before cutover, run the existing API contract tests against fixtures backed by
PostgreSQL and compare responses with the current SQLite responses:

- `/health`
- `/api/v1/scope`
- `/api/v1/tenders`
- `/api/v1/tenders/{id}`
- `/api/v1/stats`
- `/api/v1/organisations`
- `/api/v1/location-search/runs/{run_id}/tenders`

The migration must not change extraction, pagination, CAPTCHA, evidence
sanitization, classification, or response formats.

## Rollback procedure

Before cutover:

1. Keep both SQLite databases and verified backups unchanged.
2. Keep the old SQLite-backed application configuration available.
3. Record the PostgreSQL migration version and import batch identifiers.

If validation or canary operation fails:

1. Stop PostgreSQL-backed writes.
2. Repoint the backend to the original SQLite files.
3. Do not copy partial PostgreSQL writes back into SQLite.
4. Preserve PostgreSQL logs and validation output for diagnosis.
5. Drop or quarantine the failed target schemas only after investigation and
   explicit approval.

## Safe production cutover

1. Complete row-level and API-level validation.
2. Run a non-live canary write using a test database or transaction rollback.
3. Verify concurrent worker behavior and transaction retries.
4. Configure separate PostgreSQL schema search paths or explicit qualified
   table access.
5. Set database URLs through environment variables, never source code.
6. Start one backend instance first.
7. Verify health and read-only API responses.
8. Enable extraction writes only after the canary passes.
9. Monitor lock, serialization, connection-pool, and foreign-key errors.
10. Retain the SQLite backups until PostgreSQL has been proven stable.

## Required implementation changes after design approval

The current Python code uses SQLite-specific behavior and cannot be switched
only by changing a file path. A later implementation must address:

- `sqlite3` connections and row factories.
- `?` parameter placeholders.
- `lastrowid`.
- `INSERT OR IGNORE`.
- SQLite URI read-only connections.
- `PRAGMA` calls.
- `executescript`.
- `sqlite_master`, `rowid`, and `PRAGMA table_info` migration logic.
- SQLite null comparison `IS ?`.
- Environment configuration for main and location PostgreSQL URLs/schemas.
- Connection pooling and retry handling for concurrent extraction workers.

Recommended runtime dependencies are `psycopg[binary]` and optionally
`psycopg_pool`. No dependencies are installed as part of this design task.

## Unresolved compatibility questions

- Should the seven orphan occurrences remain permanently unresolved, or is
  there an approved source for later association?
- Should typed shadow timestamp columns be added later?
- Should evidence JSON remain text-only for exact archival fidelity?
- Main `source_evidence.tender_id` is a declared and enforced foreign key;
  location `source_evidence.tender_id` remains a logical relationship because
  that source schema has no declared foreign key.
- Should PostgreSQL roles separate read-only API access from extraction writes?
- Is one Neon pooled connection URL sufficient for concurrent location jobs?
- Should durable job/session state be implemented before PostgreSQL cutover?

## Readiness assessment

The schema design and migration plan are ready for implementation review.
The migration itself is not ready to execute until:

1. The orphan-occurrence policy is approved.
2. PostgreSQL adapter changes are implemented and tested.
3. Environment-variable and connection-pool design is finalized.
4. A verified backup/import/rollback rehearsal is completed.
